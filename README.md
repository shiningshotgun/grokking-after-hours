# Grokking reproduction: modular division (x / y mod 97)

A from-scratch reimplementation of one experiment from Power et al., 2022,
"Grokking: Generalization Beyond Overfitting on Small Algorithmic Datasets"
(https://arxiv.org/abs/2201.02177), following the paper's default configuration
(AdamW, lr 1e-3, weight decay 1.0, 50% data, 100,000 updates, 3 seeds).

Dataset and model architecture are adapted from the official
[openai/grok](https://github.com/openai/grok) repository (MIT license); this
project keeps the same simple flat-module layout rather than its packaging.

## Layout

```
model.py                 2-layer decoder-only transformer (width 128, 4 heads)
data.py                  modular-division dataset + tokenizer (official construction)
train.py                 training loop with checkpointing, snapshots, pause/resume
run_state.py             pure state machine shared by the trainer and its tests
                         (checkpoint validation, schedule, resume planning)
test_state_machine.py    no-workload state/checkpoint/destination tests
                         (no forward/backward passes, no optimizer steps)
evaluate_endpoints.py    inference-only 100,000-step endpoint measurement
analyze.py               plots + summaries from the retained metrics CSVs
smoke.py                 environment sanity check: versions, device, dataset
                         construction, model instantiation, one inference-only
                         forward pass (no optimizer steps, no training)
runs/seed{0,1,2}/metrics.csv   raw per-eval-point measurements (unchanged bytes)
plots/                   accuracy_curves.png, loss_curves.png
results.json             per-seed run summary (throughput, crossings, last logged)
endpoint_metrics.json    measured 100k-step endpoints + stale latest.pt cross-check
endpoint_metadata_correction.json  hash-definition correction record (see below)
requirements.txt         recorded environment versions (not a tested lockfile)
analysis_summary.json    regenerated by analyze.py
RESULTS.md               measured results, definitions, limitations
PILOT.md                 pilot-run throughput/storage report
```

## Setup

Recorded environment (what was actually used; see `requirements.txt`):
Python 3.9.6 with torch 2.8.0, numpy 2.0.2, matplotlib 3.9.4, on Apple
Silicon (MPS). If you already have such an environment, activate it and skip
installs. A fresh install is NOT a tested recipe here; the pins are a record,
not a validated lockfile:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt   # not executed in this project
```

Check the environment without training:

```bash
.venv/bin/python smoke.py
```

The state-machine tests are separate from the smoke forward check and run
without any workload:

```bash
.venv/bin/python -m unittest test_state_machine -v
```

Legacy checkpoint migration requires a trusted sidecar JSON with seed,
global_step, epoch, a 64-hex checkpoint SHA-256, and the full canonical
run_identity plus run_identity_hash. The sidecar binds claims to bytes but is
not itself authenticated; users must supply a trusted record. Missing or
inconsistent provenance blocks migration rather than being guessed.

## Training (reference only; not executed in the correction passes)

The retained `runs/seed{0,1,2}/` directories contain **only** `metrics.csv`
(the checkpoints were moved to the verified external archive). Metrics without
a matching checkpoint are NOT a resumable run directory, and the trainer
refuses to start a fresh run into them — a fresh default command can no longer
append to historical CSVs. A NEW run must target an explicitly unused
destination, e.g.:

```bash
# future runs: fresh, unused destination (illustrative; not executed here)
.venv/bin/python train.py --seed 0 --run-dir runs_future/seed0_fresh
```

Resume is attempted only when `latest.pt` exists in the destination, and it is
validated strictly (identity, counters, permutation/cursor, RNG, schedule
pointer) and cross-checked against the destination's existing metrics; a
checkpoint behind the last logged row fails closed. There is no
force-append/reset escape hatch. SIGINT/SIGTERM trigger a clean
checkpoint-and-exit (unfinished epochs are preserved mid-epoch exactly).

Resume claims are scoped: the state transitions above are covered by
`test_state_machine.py` (schedule, mid-epoch/boundary resume planning,
serialization round-trip, destination refusal). Numerical optimizer-continuation
equivalence is NOT tested, and MPS is not bitwise-deterministic anyway.

Writes are atomic (temp file + rename), and snapshots/full checkpoints are
idempotent at their step. `latest.pt` is written at eval-epoch ends and at
every exit with unsaved updates.

## Analysis from retained measurements

`analyze.py` never overwrites existing outputs; pass a new, unused output
directory/summary for future runs (illustrative; not executed here):

```bash
.venv/bin/python analyze.py --runs-dir runs --out-dir plots_future \
    --summary analysis_summary_future.json
```

No training, no optimizer steps, no checkpoint access. Missing/unmeasured
endpoint entries are reported explicitly; a partial seed subset is never
presented as the three-seed mean.

## Endpoint re-evaluation from external checkpoints

Checkpoints and snapshots are intentionally not kept in this tree; they are
preserved in a private, verified archive (SHA-256 manifest included, directory
`repo/` mirrors this project's relative paths — see the private evidence
location recorded outside this repository). To re-evaluate endpoints from
those checkpoints, pass the archive's `repo/` directory explicitly — nothing
is downloaded automatically:

```bash
.venv/bin/python evaluate_endpoints.py --artifact-root /path/to/archive/repo \
    --out /tmp/endpoint_rerun.json     # --out is required and must not exist
```

`--artifact-root` defaults to `.` (i.e. in-tree `runs/`), which contains only
the metrics CSVs, so absent snapshot inputs are reported as explicit
"unmeasured" per-seed entries rather than crashes. The retained
`endpoint_metrics.json` is the measured record; reruns must write to a new,
unused `--out` path (the tool refuses to overwrite existing files).

## Fidelity notes

- Vocab is 239 (official `grok/data.py` construction: EOS + "=" + 20 operator
  keys + residues 0–96 + 120 S5 permutations). Parameter count 455,424.
- Eval cadence follows official code: `next = max(int(1.02 * e), e + 1)`.
  Fresh runs start with the epoch-0 cadence.
- Built-in PyTorch AdamW vs the official custom optimizer is an implementation
  difference, not a demonstrated cause of any behavioral difference.
- Device: MPS (Apple Silicon). MPS is not bitwise-deterministic; runs are not
  claimed bitwise-exact.
- Scoring contract: after the "=", the model is scored on exactly TWO tokens
  per equation — the answer residue and the EOS token (one answer token plus
  EOS). Accuracy is equation-level (both scored tokens correct).
- `endpoint_metrics.json` metadata shows `hash_matches_expected: false`. The
  reason is a hash-DEFINITION mismatch, not a data mismatch: the endpoint
  script hashed a 2-field config prefix (`c4625d6b…`) while the expected
  constant is the training-time 5-field hash (`b594e735…`). The two digests
  are computed over the SAME dataset bytes with DIFFERENT config prefixes and
  are therefore different; an earlier claim that the two hashes were
  "recomputed and confirmed identical" was wrong and has been removed. See
  `endpoint_metadata_correction.json` for both definitions, the byte layout,
  and the independent recomputation record. The script now uses the
  training-time 5-field definition and records it in new outputs.

## Status

Seeds 0, 1, 2 ran to 100,000 steps. True 100k-step endpoints were measured
inference-only from the step-100000 snapshots (`endpoint_metrics.json`); the
`latest.pt` checkpoints had stopped at ~98.9–99.1k steps and are reported
separately as stale. CSV rows and `results.json` describe **last-logged**
values (~98.9–99.1k steps), not the 100k endpoints. The state-machine fixes in
`train.py`/`run_state.py` are future-behavior corrections: they did not
produce the original runs and cannot retroactively repair the archived
final-state optimizer/RNG state. See RESULTS.md for measured results and
limitations.
